# Vercel + Neon research deployment

This deployment adapts the prototype to request-scoped Vercel FastAPI functions rather than persistent bank containers. The frontend is a static Vite deployment. The coordinator and each of the three banks are separate Vercel projects. The bank endpoints require independent client keys and HTTPS; the frontend proxies `/api/*` to the coordinator on the same browser origin.

One newly provisioned Neon Free database holds four isolated PostgreSQL schemas. Each service logs in with its own restricted role and default schema. The coordinator role has no usage privilege on bank schemas; bank roles have no access to each other. The provisioning owner connection is removed from runtime project variables after setup. No raw synthetic transaction arrays are stored in the coordinator database or uploaded with the frontend.

Bank functions reconstruct their deterministic synthetic cohorts in their own `/tmp` space. Only model weights, version/replay metadata, and privacy accounting history persist in that bank's Neon schema. Database transactions and bank-specific transaction advisory locks protect model updates, privacy accounting and replay behavior across function instances. There is no dependence on an ephemeral local SQLite ledger in the cloud.

The cloud bank functions use Google's supported `dp-accounting` RDP accountant for the same full-batch clipped Gaussian gradient mechanism, with q=1 and add/remove adjacency. Local development still supports Opacus. The cloud adapter avoids bundling PyTorch solely to import an accountant. It does not change the documented fixed public denominator, clipping/noise mechanism, non-cryptographic RNG limitation, or absence of cryptographic secure aggregation.

In `SERVERLESS=true` mode, federated rounds finish inside the API invocation. A PostgreSQL advisory lock serializes concurrent rounds across coordinator instances; the connection uses Neon's non-pooling endpoint so session-level locking is meaningful. The API responds after training completes, and the UI then displays the persisted round. Other local workflows retain their existing background dispatch behavior. Request-scoped functions are capped at 300 seconds; no claim is made for arbitrarily long training jobs. Longer jobs need a durable external job system.

`CLOUD_SCHEMA_READY=true` skips per-invocation schema creation/seeding and restart cleanup. Provisioning initializes the coordinator schema once with its own restricted role. Cold starts therefore do not mark unrelated active jobs failed or reseed accounts. The deployment script is `scripts/deploy_neon.py`; it stages source under ignored `runtime/cloud/*`, configures encrypted runtime variables, deploys bank projects, seeds the coordinator, then deploys the API. Provisioning state and credentials stay in ignored runtime files and never enter frontend assets. Deploying the frontend is the separate `scripts/prepare-vercel.mjs --backend-url ...` step.

This is still a synthetic research deployment, not production bank infrastructure. Authentication limits remain process-local, formal privacy/security validation is absent, audit records are mutable, and the database owner plus cloud account administrators remain trusted. Vercel's existing deployment protection settings are preserved. Production domain reachability does not make bank training endpoints unauthenticated.
